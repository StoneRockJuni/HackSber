# Обработка персональных данных и 152-ФЗ

**Команда:** hackSber  
**Статус документа:** проектные решения для прототипа, не юридическое заключение. Перед пилотом с реальными данными документ согласуется с юристами и ИБ банка.

## 1. Принципы

1. **Законная цель.** Данные обрабатываются только для мониторинга залогового объекта ИЖС и принятия кредитного решения.
2. **Минимизация.** В паспорт снимка не попадают ФИО, паспортные данные, точный адрес и телефон. Вместо клиента используется псевдоним `client_id`.
3. **Псевдонимизация.** Соответствие `client_id → клиент` хранится в отдельной таблице АС банка с ограниченным доступом. В паспорте и аудите — только псевдоним.
4. **Локализация.** Обработка и хранение — в контуре банка на территории РФ. Внешние API по умолчанию отключены.
5. **Подотчётность.** Каждое решение фиксируется в журнале аудита с хэшем снимка, автором и основанием.
6. **Безопасность.** Доступ к снимкам, паспортам и журналу — по ролям; журнал append-only; целостность проверяется `verify_audit_chain`.

## 2. Какие данные обрабатываются

| Категория | Пример | Где хранится | Правовой режим |
|---|---|---|---|
| Персональные данные заёмщика | ФИО, телефон, адрес, кредитный договор | АС банка | ПДн, 152-ФЗ |
| Псевдоним клиента | `CL-2026-004217` | Паспорт снимка, аудит | Обезличенные данные |
| Аэрофотоснимок | Дом, участок, лица/машины на фоне | Хранилище банка | Может содержать ПДн |
| EXIF/GPS | Координаты, время, модель БПЛА | Внутри файла и в паспорте | Метаданные, связанные с объектом |
| Данные полётного задания | `flight_task_id`, оператор, QR-маркер | Паспорт, журнал | Служебные данные |
| Журнал аудита | actor, action, object_hash, decision | `audit_trail.jsonl` | Служебные данные, могут быть доказательством |

**Правило:** если на снимке видны лица, номера автомобилей или окна соседних домов, перед передачей в кредитный комитет применяется маскирование. В прототипе маскирование не автоматизировано — это ручной шаг и остаточный риск.

## 3. Роли и доступ

| Роль | Снимки | Паспорт | Журнал аудита | Настройки | Решение |
|---|---|---|---|---|---|
| Инспектор ИЖС | Просмотр своих объектов | Просмотр | Нет | Нет | Готовит проект |
| Риск-менеджер | Просмотр | Просмотр | Просмотр | Нет | Утверждает/отклоняет |
| Аудитор | Просмотр по запросу | Просмотр | Просмотр + проверка цепочки | Нет | Нет |
| Администратор ИБ | Нет бизнес-доступа | Нет | Технический доступ | Да | Нет |
| Подрядчик-оператор БПЛА | Загрузка своих снимков | Создание | Нет | Нет | Нет |
| Клиент | Нет | Нет | Нет | Нет | Получает уведомление |

**Принцип четырёх глаз:** решение по траншу не должно приниматься одним сотрудником. В прототипе кнопка «Утвердить» имитирует действие риск-менеджера; в промышленной версии требуется отдельная подпись.

## 4. Цели и правовые основания

- **Цель:** проверка фактического состояния залогового объекта, контроль сроков строительства, снижение риска мошенничества.
- **Основание:** кредитный договор и согласие субъекта ПДн на дистанционный мониторинг; для банка — исполнение договора и законные интересы при условии соблюдения 152-ФЗ.
- **Специальные категории ПДн** (здоровье, биометрия) не обрабатываются. Биометрическая идентификация по фото не выполняется.
- **Трансграничная передача** не требуется: внешний VLM отключён по умолчанию.
- **Локальный AI:** YOLOv8n SberStroi работает как ONNX-файл на ноутбуке/сервере банка; снимок не отправляется вендору модели. В аудит пишется SHA-256 весов, чтобы решение можно было воспроизвести.

## 5. Сроки хранения (предлагаемые по умолчанию)

| Данные | Срок | Обоснование |
|---|---|---|
| Аэрофотоснимки | 5 лет с даты решения или до конца срока кредита | Доказывание и кредитная история |
| Паспорт снимка | 5 лет | Связь снимка с решением |
| Журнал аудита | 5 лет, но не меньше срока хранения кредитного досье | Аудит и расследование инцидентов |
| Черновики/временные файлы | Не более 24 часов | Минимизация |
| Логи внешнего VLM | Не создаются (сервис отключён) | Исключение передачи |
| Веса ONNX и метаданные модели | Срок эксплуатации + 1 год | Воспроизводимость AI-решения и разбор инцидентов |

Сроки — проектное предложение. Перед пилотом их нужно сверить с политикой банка и требованиями регулятора.

## 6. Меры защиты (152-ФЗ, ст. 19)

1. **Организационные:** приказ о ролях, инструкция инспектора, журнал доступа, обучение.
2. **Технические:** локальный контур, шифрование диска, ограничение сетевого доступа, секрет-менеджер для `PASSPORT_SIGNING_KEY`.
3. **Прикладные:** псевдонимизация, хэширование файлов, аудит-цепочка, проверка QR/GPS, лимит загрузки.
4. **Мониторинг:** ежедневная проверка `verify_audit_chain`, алерт на расхождение head-хэша, разбор инцидентов.
5. **Резервирование:** ежедневная копия журнала в WORM-хранилище; хэш head выгружается во внешний регистр.

## 7. Инциденты

**Сценарии:** утечка снимков, подмена журнала, компрометация учётной записи подрядчика, отправка данных во внешний сервис.

**Порядок по умолчанию:**
1. Остановить обработку и изолировать узел.
2. Сохранить копию журнала и head-хэш.
3. Уведомить ИБ банка и ответственного за ПДн.
4. Оценить категорию и масштаб; при необходимости уведомить Роскомнадзор в сроки, установленные законом.
5. Устранить причину, обновить модель угроз, провести разбор.

В прототипе нет выделенного security-контакта, поэтому **предлагаем назначить владельцем инцидента руководителя ИБ банка** и зафиксировать это в регламенте до пилота.

## 8. Права субъектов ПДн

Клиент вправе запросить сведения об обработке, доступ к своим данным, уточнение, блокирование или уничтожение, если нет законных оснований для хранения. Запрос обрабатывается через АС банка; паспорт снимка содержит только псевдоним и не позволяет идентифицировать клиента без маппинга.
