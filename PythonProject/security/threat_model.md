# Модель угроз «СтройКонтур»

**Команда:** hackSber  
**Кейс:** дистанционный мониторинг объектов ИЖС по аэрофотоснимкам БПЛА  
**Границы прототипа:** ноутбук инспектора, локальные файлы, Streamlit-интерфейс, модуль `security.py`, локальная ONNX-модель YOLOv8n SberStroi. Внешние API по умолчанию не используются.

## 1. Что защищаем

| Актив | Почему важен | Где находится |
|---|---|---|
| Аэрофотоснимок | Доказательство состояния объекта и основания для транша | Файловая система / хранилище банка |
| EXIF и GPS | Подтверждение места и времени съёмки | Внутри файла снимка |
| Паспорт снимка | Связывает файл, объект, полётное задание и оператора | JSON в `security/sample_passport.json` |
| Журнал аудита | Доказывает, кто и на каком основании принял решение | `audit_trail.jsonl` |
| Кредитное досье | Содержит персональные данные заёмщика | АС банка, вне прототипа |
| Модель/правила маршрутизации | Влияет на кредитное решение | `vision_agent.py`, `director.py` |
| Веса YOLOv8n SberStroi | Определяют стадию 0/50/100% | `models/sberstroi_yolov8n.onnx` + JSON-метаданные |

## 2. Доверенные границы

1. **Борт БПЛА и карта памяти** — источник EXIF/GPS. Считаем условно доверенным, пока устройство не скомпрометировано.
2. **Канал передачи подрядчик → банк** — не доверенный. Файл может быть изменён, переименован или заменён.
3. **Контур банка** — доверенная среда: здесь считаются хэши, строится паспорт и пишется аудит.
4. **Рабочее место инспектора** — полу-доверенное: человек может ошибиться или обойти проверку вручную.
5. **Внешний VLM (Gemini)** — не доверенный и по умолчанию отключён; с реальными ПДн не используется.

## 3. Угрозы и контрмеры

| ID | Угроза / сценарий | Вектор | Контрмера в прототипе | Остаточный риск |
|---|---|---|---|---|
| T1 | Подмена снимка после съёмки | Старый или чужой файл выдаётся за новый | `compute_image_hash` + паспорт: SHA-256 по всем байтам файла | Хэш не доказывает, что файл создан именно в момент съёмки |
| T2 | Редактирование EXIF/GPS | Правка координат или даты в файле | Хэш меняется вместе с EXIF; `verify_exif_gps_match` сверяет точку с кадастром | Скомпрометированный БПЛА может сразу записать ложные EXIF |
| T3 | Повторное использование валидного снимка (replay) | Старое фото с тем же QR | Одноразовый `expected_marker` на полётное задание, `check_challenge_marker` | Если QR физически скопирован на объект, нужна ротация маркера |
| T4 | Подделка QR/цветового маркера | Печать копии маркера | QR проверяется OpenCV; цветовой маркер помечен как demo-stub | Криптографически QR не подписан; нужен динамический токен |
| T5 | Компрометация учётной записи подрядчика | Украденный логин/токен | Разделение ролей, обязательный `actor` в аудите, журнал решений | В прототипе нет полноценной аутентификации |
| T6 | Инсайдер меняет решение | Ручная правка JSON перед утверждением | Аудит фиксирует решение, объект и хэш; `verify_audit_chain` ловит правку журнала | Инсайдер с правами на файл может удалить весь журнал |
| T7 | Подмена или удаление записей аудита | Правка `audit_trail.jsonl` | `hash_prev` + `record_hash`, проверка всей цепочки | Обнаруживается правка/удаление в середине, но не удаление хвоста |
| T8 | Утечка ПДн через паспорт | ФИО/адрес попадают в JSON и логи | В паспорте только псевдоним `client_id`; маппинг хранится отдельно | Сами снимки могут содержать лица, номера машин, адреса |
| T9 | Отправка данных во внешний сервис | Инспектор вводит API-ключ VLM | Внешний вызов требует явного `ALLOW_EXTERNAL_VLM=1`; в UI предупреждение | Пользователь с правами на окружение может включить внешний режим |
| T10 | Некорректный файл/DoS | Огромный или битый файл | Проверка `cv2.imdecode`, отказ от анализа, аудит ошибки | Нет жёсткого лимита размера в прототипе |
| T11 | Подмена зависимости | Вредоносный пакет в окружении | Фиксированный `requirements.txt`, локальный запуск, без внешних API | Нет проверки подписей пакетов и SBOM |
| T12 | Ошибка модели/правил | Ложный вердикт по качественному снимку | Human-in-the-Loop, объяснение решения, аудит | Модель не сертифицирована; решение должен подтверждать человек |
| T13 | Подмена весов модели | Атакующий заменяет `.onnx`, чтобы менять стадию | SHA-256 весов пишется в `_meta.ai` и в аудит; путь задаётся `SBER_YOLO_MODEL` | Нет подписи артефакта и контроля доступа к папке `models/` |
| T14 | Снимок вне обучающего распределения | Интернет-фото, другой регион, ракурс, сезон, рендер | Confidence-порог; при отсутствии детекций — `needs_manual_review` и стратегия 3, а не «0%» | 40 train / 10 val изображений не доказывают устойчивость |
| T15 | Отравление обучающих данных / утечка валидации | Подмена разметки или split по почти одинаковым кадрам | Split по целым полётным сериям, версия датасета, фиксация метрик в JSON | Нет независимого аудита датасета и происхождения разметки |
| T16 | Prompt injection через изображение (VLM) | Текст на фото пытается переопределить инструкции VLM | Внешний VLM выключен по умолчанию; локальный YOLO не исполняет текст; ответ VLM валидируется по схеме | При включённом VLM нет отдельной защиты от malicious prompt |
| T17 | Состязательное изображение | Патч/шум заставляет YOLO увидеть «крышу» | Human review, quality gate, аудит модели и решения | Специальной adversarial-защиты в прототипе нет |
| T18 | SSRF через «проверить фото по ссылке» | Пользователь вставляет `http://10.0.0.5/admin` или `http://169.254.169.254/...`, приложение ходит во внутреннюю сеть | `net_safe.py`: только http/https, запрет приватных/локальных адресов после DNS-резолва, повторная проверка каждого редиректа, лимит 25 МБ / 20 с / 3 редиректа, проверка magic bytes вместо `Content-Type` | DNS rebinding (резолв в публичный адрес при проверке и приватный при соединении); для пилота — egress-прокси с allow-list и пиннинг IP |
| T19 | DoS через URL или «декомпрессионную бомбу» | Огромный файл или картинка с гигантским числом пикселей | Лимит размера скачивания и таймаут; изображение декодируется локально | Нет антивируса и лимита на число пикселей при декодировании |
| T20 | Утечка ПДн через «песочницу» | Сотрудник загружает личное или чужое фото в интерфейс проверки | Обработка только локальная, ничего не отправляется, в UI явное предупреждение | Нет DLP и технического запрета на личные файлы |

## 3.1. Откуда берётся GPS и что он доказывает

Координата читается только из самого файла (`security.gps_provenance`):
EXIF GPS IFD → XMP-пакет → имя файла → «нет». Проверяются датум WGS-84,
активный фикс (`GPSStatus = A`), отсутствие `0,0`, расхождение EXIF и XMP
(признак подмены), расхождение с именем файла. Ни IP-геолокации, ни карт, ни
данных устройства не используется.

Важно для оценки риска: **GPS в EXIF — это утверждение файла, а не факт
съёмки**. Он доказывает «что записано», но не «кто, когда и по какому адресу
снимал». Доказательство даёт связка «файл + одноразовый QR полётного задания +
полётное задание + кадастровая точка», а не сам EXIF.

## 4. Что сознательно не входит в прототип
- Полноценная аутентификация и RBAC на уровне UI.
- Аппаратная подпись снимка на борту БПЛА.
- WORM-хранилище и внешний якорь для аудита.
- Автоматическое распознавание и маскирование лиц/номеров.
- Юридически значимая квалифицированная ЭП.
- Промышленная валидация YOLO на полевом датасете, adversarial-тесты и мониторинг drift.
- Подпись и SBOM для весов модели.

Эти пункты вынесены в дорожную карту и названы честно: прототип показывает **контролируемый контур доверия**, а не готовую промышленную СЗИ.

## 5. Приоритет внедрения

1. Включить `PASSPORT_SIGNING_KEY` и хранить ключ в секрет-менеджере.
2. Ограничить доступ к `audit_trail.jsonl` и настроить ежедневную выгрузку head-хэша во внешний регистр.
3. Добавить аутентификацию и роли до пилота с реальными ПДн.
4. Ввести лимит размера файла и антивирусную проверку загрузок.
5. Подписывать ONNX-артефакт и хранить его hash в аудите; добавить SBOM.
6. Собрать полевой датасет по региону, провести слепую валидацию по объектам и мониторинг drift.
7. Провести DPIA и согласовать сроки хранения с юристами банка.
