# Модель угроз «СтройКонтур»

**Продукт:** AI-платформа мониторинга строительства ИЖС с помощью дронов.
**Контур:** on-premise, без внешних API. Снимки и персональные данные не покидают инфраструктуру банка.
**Версия:** 1.0 (хакатон `{Sib}Код`, кейс 3).
**Связанные артефакты:** `security.py`, `security/audit_schema.json`, `security/privacy_152fz.md`.

> Модель угроз описывает **остаточный риск**, а не обещает абсолютную защиту. Hash-chain делает журнал tamper-evident; tamper-proof достигается только WORM-хранилищем, KMS/HSM и внешним анкором head-hash в контуре банка.

---

## 1. Что защищаем

| Актив | Почему важен | Где находится |
|---|---|---|
| Файл аэрофотоснимка | Доказательство состояния залога, основание для решения по кредиту | Object storage внутри контура |
| EXIF/GPS и телеметрия | Привязка снимка к участку и полётному заданию | Метаданные рядом со снимком / БД |
| «Паспорт снимка» | Юридически значимое описание происхождения снимка | PostgreSQL/JSONB + API |
| Audit Trail | Доказуемость решений AI-Дирижёра и инспектора для банка и аудита | Append-only JSONL + WORM-копия |
| Идентификаторы клиента | Связь объекта с кредитным делом | Отдельный защищённый реестр, не в паспорте |
| Ключи HMAC/KMS | Целостность паспорта и журнала | KMS/HSM, не в коде и не в git |

**Персональные данные в снимке:** фасад дома, участок, номера машин, лица прохожих, соседние участки. Поэтому снимок считаем ПДн и применяем 152-ФЗ, даже если в JSON только `client_id`.

## 2. Границы доверия

```text
[Дрон/подрядчик] --TLS/mTLS--> [Шлюз загрузки] --внутренняя сеть--> [Сервис паспортизации]
                                      |                                      |
                                      v                                      v
                              [Object Storage]                       [security.py]
                                      |                          hash / EXIF / marker / passport
                                      v                                      |
                              [AI-Дирижёр on-prem] <----------------------+
                                      |
                                      v
                              [Инспектор: решение]
                                      |
                                      v
                         [Audit Trail JSONL] --nightly--> [WORM / анкор в банке]
```

**Доверенные компоненты:** шлюз загрузки, сервис паспортизации, KMS/HSM, WORM-хранилище, сервер точного времени.
**Недоверенные:** файл снимка, EXIF, GPS, имя файла, сайдкары телеметрии, QR-маркер, клиентские timestamp, пользовательский ввод.

---

## 3. Модель нарушителя

1. **Внешний атакующий** — подделывает снимок/метаданные, перехватывает загрузку, пытается внедрить malicious-файл.
2. **Недобросовестный подрядчик** — снимает чужой объект, берёт старое фото, подменяет GPS/телеметрию, продаёт доступ.
3. **Инсайдер** — инспектор/риск-офицер/администратор, который пытается изменить решение, удалить запись или выгрузить ПДн.
4. **Скомпрометированная учётка/сервис** — злоумышленник действует от имени легитимного пользователя.
5. **Ошибка/сбой** — битый EXIF, обрыв записи, рассинхронизация часов, сбой диска.

## 4. Таблица угроз и контрмер

| ID | Угроза | Вектор атаки | Контрмера (код/механизм) | Остаточный риск |
|---|---|---|---|---|
| T01 | Подмена файла снимка | Заменить JPEG после съёмки, пересохранить пиксели | `compute_image_hash()` — SHA-256 по байтам; хэш фиксируется в паспорте и Audit Trail; при проверке хэш пересчитывается | Если подмена произошла **до** первого хэширования, исходность не доказать. Нужна доверенная загрузка/attestation |
| T02 | Подделка EXIF/GPS | Отредактировать GPS, дату, модель камеры | SHA-256 фиксирует любое изменение файла; `verify_exif_gps_match()` сверяет GPS с кадастром; `build_snapshot_passport()` фиксирует источник GPS и warning | EXIF можно подделать до загрузки; GPS-спуфинг дрона не ловится только по EXIF |
| T03 | Снимок чужого объекта | Прислать фото другого дома/участка | GPS-допуск 30 м + `cadastral_gps` + `flight_task_id` + AI-проверка геометрии/контекста + ручное подтверждение инспектора | Ошибка кадастровых координат и плотная застройка; нужна сверка с ГЕО-слоем и несколькими ракурсами |
| T04 | Старое фото вместо сегодняшнего | Взять архивный снимок из интернета/прошлой проверки | Одноразовый `expected_marker` с TTL 15–30 мин на полётное задание; `check_challenge_marker()`; `captured_at`; дубликаты по SHA-256 | Маркер можно сфотографировать с экрана/распечатки; нужен динамический QR + liveness/цветовой паттерн |
| T05 | Реплей полётного задания | Повторно загрузить старый файл с тем же ID задания | Уникальность `flight_task_id` + nonce маркера + проверка дубликата SHA-256 + `uploaded_at` | Если маркер/токен задания украден — окно реплея до истечения TTL |
| T06 | Подделка QR/цветового маркера | Напечатать QR, показать с экрана, наклеить на объект | QR содержит одноразовый токен; сравнение `hmac.compare_digest`; TTL; привязка к полётному заданию; в production — динамический экран/AR-маркер | Физическая подделка маркера; нужна проверка глубины/перспективы и случайного паттерна |
| T07 | MITM при загрузке | Перехват трафика подрядчика | TLS 1.2+/mTLS, scoped upload token, подпись батча, загрузка только в доверенный шлюз | Компрометация устройства подрядчика; нужна device attestation |
| T08 | Кража учётной записи подрядчика | Фишинг, переиспользование пароля | MFA, короткоживущие токены, RBAC, ограничение по `flight_task_id`, аномалии загрузок | Угон активной сессии; нужен step-up auth и поведенческая аналитика |
| T09 | Изменение Audit Trail | Отредактировать `decision`, `actor`, `timestamp` в JSONL | `write_audit_log()`: `hash_prev` + `hash_self`; `verify_audit_chain()` пересчитывает всю цепочку; `seq` без пропусков; optional HMAC | Без HMAC/внешнего анкора атакующий с правами на файл может пересчитать всю цепочку |
| T10 | Удаление/обрезка журнала | Удалить последние записи, очистить файл, truncate | Append-only `O_APPEND`, file lock, fsync, права `0600`; проверка `AUDIT_EXPECTED_COUNT`/`AUDIT_EXPECTED_HEAD`; nightly anchor в WORM | Локальный администратор с root может удалить файл; WORM/отдельный контур обязателен в production |
| T11 | Инсайдер меняет решение | Инспектор переписывает вердикт задним числом | Новое решение = новое событие, старое не удаляется; `actor_role`; разделение ролей; read-only аудитор; four-eyes для высокого риска | Сговор двух сотрудников; нужен независимый контроль и выборочный аудит |
| T12 | Утечка ПДн | Скачать снимки, выгрузить mapping, передать во внешний сервис | Псевдонимизация `client_id`; mapping в отдельном реестре; RBAC/ABAC; no PII in QR; on-prem; шифрование; логирование доступа | Координаты и фасад сами по себе могут идентифицировать субъекта; нужна оценка DPIA и маскирование |
| T13 | Path traversal / чтение чужих файлов | Передать `../../etc/passwd` в `image_path` | `image_path` формируется только доверенным сервисом; API принимает `snapshot_id`, не путь; `Path.is_file()`, запрет symlink для audit log | Ошибка в вышестоящем сервисе; нужна валидация на API-шлюзе и allow-list каталогов |
| T14 | Malicious-файл / decompression bomb | Огромный JPEG, битый TIFF, эксплойт парсера | Лимиты EXIF 4 МБ, JPEG scan 64 МБ, sidecar 1 МБ, количество IFD-записей; `cv2` опционален; обработка в изолированном worker | 0-day в OpenCV/декодере; нужен sandbox/container и обновление зависимостей |
| T15 | Компрометация HMAC-ключа | Кража env/файла ключа | Ключ только из env/KMS/HSM, минимум 32 байта, ротация, разделение ключей audit/passport, запрет в git | Компрометация KMS/администратора; нужен HSM и dual control |
| T16 | Манипуляция временем | Подмена системных часов, «состаривание» события | `timestamp` ставит сервер в UTC; клиентский timestamp только в `details.claimed_timestamp`; GPS UTC как второй источник; NTP/защищённое время | Компрометация сервера времени; нужен доверенный PTP/NTP и мониторинг дрейфа |
| T17 | Prompt injection / отравление AI | Вредоносный текст в метаданных/имена файлов, подсказка модели | Не передавать сырые имена/EXIF в LLM; on-prem модель; фиксированный промпт; AI только предлагает решение; финальное решение — человек | Модель может ошибиться; нужен human-in-the-loop и confidence threshold |
| T18 | Supply chain | Вредоносный пакет/обновление | Offline-установка, lock-файлы, SBOM, проверка хэшей, минимальные зависимости, подпись артефактов | Компрометация внутреннего репозитория; нужен trusted build |
| T19 | Потеря/порча хранилища | Сбой диска, ransomware | Репликация, immutable backups, versioning, WORM, restore-тесты | Ransomware с правами администратора; нужна изоляция бэкапов |

## 5. STRIDE-покрытие (кратко)

| STRIDE | Пример | Основные контрмеры |
|---|---|---|
| **S**poofing | Чужой подрядчик, чужой дрон | mTLS, MFA, `drone_id`, `flight_task_id`, operator attestation |
| **T**ampering | Подмена фото/EXIF/журнала | SHA-256, `hash_prev`, HMAC, WORM |
| **R**epudiation | «Я не принимал решение» | Audit Trail с actor/action/decision, подпись, неизменяемость |
| **I**nformation disclosure | Утечка ПДн | Псевдонимизация, RBAC, on-prem, шифрование |
| **D**enial of service | Огромный файл/битый TIFF | Лимиты, sandbox, очередь, rate limit |
| **E**levation of privilege | Инспектор получает права аудитора | RBAC/ABAC, разделение обязанностей, MFA |

## 6. Chain of Custody: контрольные точки

| Шаг | Событие | Кто/что фиксирует | Артефакт |
|---|---|---|---|
| 1 | Выдано полётное задание и одноразовый маркер | Сервис заданий | `flight_task_id`, marker TTL |
| 2 | Дрон/подрядчик загрузил файл | Шлюз загрузки | TLS-сессия, `drone_id`, `operator_id` |
| 3 | Хэш посчитан в доверенном контуре | `compute_image_hash()` | `snapshot.sha256` |
| 4 | Разобраны EXIF/GPS или телеметрия | `build_snapshot_passport()` | `location.gps`, `source_metadata` |
| 5 | GPS сверен с кадастром | `verify_exif_gps_match()` | `cadastral_check` |
| 6 | Проверен челлендж-маркер | `check_challenge_marker()` | `challenge_marker.status` |
| 7 | Выдан паспорт и QR-ссылка | `build_snapshot_passport()` | `passport_id`, `passport_sha256` |
| 8 | AI-Дирижёр предложил решение | Сервис AI | `write_audit_log()` |
| 9 | Инспектор принял решение | UI инспектора | `write_audit_log()` |
| 10 | Ночной анкор head-hash | Cron/сервис аудита | WORM + `AUDIT_EXPECTED_HEAD` |
| 11 | Аудитор проверил цепочку | `verify_audit_chain()` | Отчёт аудита |

## 8. Остаточные риски и план production

1. **Нет HSM/KMS в прототипе.** HMAC-ключ берётся из env/файла. В production — KMS/HSM, ротация, dual control, отдельные ключи для audit и passport.
2. **Нет WORM в прототипе.** JSONL можно удалить локально. В production — S3 Object Lock / WORM, ежедневный анкор `head` и `count` в отдельном контуре банка.
3. **Нет подписи ГОСТ.** Для юридической значимости — КЭП/ГОСТ 34.10-2012, квалифицированная метка времени, C2PA-подпись снимка на устройстве.
4. **GPS можно спуфить.** Нужна сверка EXIF + RTK-телеметрии + IMU + геометрии кадра, а также контроль зоны полёта.
5. **QR можно сфотографировать с экрана.** Нужен динамический маркер, случайный цветовой паттерн, проверка перспективы/бликов, TTL и привязка к заданию.
6. **Модель AI может ошибаться.** AI-Дирижёр только предлагает; финальное решение и ответственность — у инспектора; confidence threshold и выборочный аудит.
7. **ПДн в кадре.** Нужен on-prem pipeline блюринга лиц/номеров/соседних участков и DPIA до промышленной эксплуатации.
8. **Supply chain.** Offline-сборка, SBOM, подпись артефактов, минимальные зависимости, регулярное обновление OpenCV.
